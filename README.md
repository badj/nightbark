                                      Find the tests that did not bark

---

```gherkin
Gregory: "Is there any point to which you would wish to draw my attention?"
Holmes: "To the curious incident of the dog in the night-time."
Gregory: "The dog did nothing in the night-time."
Holmes: "That was the curious incident."
— Silver Blaze

The dog did not bark, so the intruder was known to it, so it was the trainer.
The absence of a signal was the evidence.

That is what this tool is for. A test that did not fail may be proving nothing 
— and a suite that is suspiciously green is a dog that did not bark.
`nightbark` goes looking for the ones that should have barked and didn't.
```

## The problem it exists for

Most test tooling helps you write more tests. Almost none helps you find out whether the tests you
have are **capable of failing**. These all pass, and all of them are worthless:

| Shape | Why it passes | Why it proves nothing |
| --- | --- | --- |
| A locator that matches nothing | `expect(x).toBeHidden()` on a selector that was renamed | Hidden because absent, not because the app hid it |
| A guard whose premise is unasserted | "the 31st request is refused" | Nobody checked the first 30 were accepted |
| A route matcher pinned to a stale path | It waits, times out, reports "never arrived" | Or worse, fails *open* and reports success |
| A detector that cannot fire | A fingerprint for a change that shipped | Reports "not deployed" forever |
| An assertion written from observed behaviour | The app does X, so the test asserts X | Asserts the bug, not the contract |

Every one of those is a dog that did not bark.

## The three primitives

**The Irregulars** — read-only auditors, dispatched in parallel, each with a narrow brief. They
report findings with file and line; they never edit. Holmes's Baker Street Irregulars were exactly
this: cheap, bounded, sent out to gather evidence, and trusted only to report back.

**Gates** — a discipline that matters ships as an *executable check*, never as prose. See
[ADR-0002](docs/adr/0002-gates-not-prose.md); this is the single most important decision in the
project and it was arrived at by experiment, not taste.

**Moriarty** — the adversarial pass. Every finding an Irregular raises gets attacked before it is
reported, because a confident wrong finding costs more trust than a missed one.

## The loop

Gates are deterministic and need nothing. The Irregular adds judgement, and **Moriarty decides what
you actually read** — measured, that is the difference between 33% and 100% precision.

```
nightbark audit <repo> --sarif out.json          # gates only. No model, no key, no network.

nightbark brief vacuity <repo> --out brief.md    # candidates + context + resolved locators
  → any agent judges each: established | absent | uncertain          → answers.json
nightbark challenge <repo> answers.json --out challenge.md
  → Moriarty attacks each claim: confirmed | downgraded | dropped    → verdicts.json
nightbark verdict <repo> --answers answers.json --verdicts verdicts.json --sarif out.json
```

What reaches a reader:

| Verdict | Reported as |
| --- | --- |
| `confirmed` | **warning** — survived an attack |
| `downgraded` | **note** — says plainly it needs a human read |
| `dropped` | **nothing.** Moriarty broke it; nobody should spend a minute on it |
| no verdict | **note, flagged UNREVIEWED** — ⚠️ skipped is not the same as cleared |

That last row is deliberate. Silently dropping an unreviewed claim would make an *incomplete*
adversarial pass indistinguishable from a clean one, which is the exact defect shape this tool is
named after.

## Usage

```bash
nightbark init <dir>                   # scaffold a suite whose disciplines are structural
nightbark audit <path>                 # run the gates over a repo (read-only)
nightbark audit <path> --gate <id>     # one gate
nightbark audit <path> --sarif out.json  # SARIF 2.1.0 for CI annotation
nightbark audit <path> --fail-on warning # exit policy: error (default) | warning | note | never
nightbark selftest                     # prove every gate can fire, and is specific
nightbark selfcheck                    # enforce ADR-0001 on this repo — no client content
nightbark verdict <path> --answers a.json --verdicts v.json   # merge into findings + SARIF
npm run selftest                       # the above, plus the output-format tests
```

**SARIF is the integration strategy, not an afterthought.** One serialiser buys GitHub Code Scanning
annotations *on the pull-request diff*, Azure DevOps ingestion, and VS Code problem matchers — with
no destination-specific code. See [INTEGRATIONS](docs/INTEGRATIONS.md).

⚠️ `--fail-on` defaults to **`error`**, not `warning`. A tool whose first run reds somebody's
pipeline gets removed from the pipeline; tighten it once the output has earned trust.

## Publishing results — `TestCaseSink`

SARIF and JUnit cover reporting, because the ecosystem already reads them. *"Record this outcome
against case 865914 in plan 764570"* has no interchange format, so it needs real code — and this is
the **one** place a bespoke adapter is justified.

```bash
nightbark sink:ado --org <o> --project <p> --plan <id> --case <id> [--suites a,b]
```

**Read-only without `--arm`.** It resolves each case to its test point(s) and tells you whether the
scope matches anything at all.

⚠️ **That read-only mode is the point of the command.** The failure it exists for is a scope that has
gone *stale*: the plan gets reorganised, the scoped suite ids stop matching any test point, and the
publish reports every case as a tick **while writing nothing**. There is no way to see that in a
normal run's output, so *"it ran green"* is not evidence anything was recorded. Run the check first.

Five behaviours the interface mandates of any adapter, because each one has bitten somebody:

| | |
| --- | --- |
| **Dry run by default** | Test-management systems have no undo |
| ⛔ **Zero matches is a FAILURE** | Not a clean run. This is the stale-fence defect, and it is the reason the interface specifies behaviour rather than just method names |
| **Distinguish 401 / 403 / 404** | Expired token, missing permission, wrong plan — three different fixes. ADO also answers 404 for a plan you cannot *see*, so that message says it may be permissions wearing a 404 |
| **Paginate** | Page one always looks complete |
| **Never invent an id** | Publishing to a guessed point is worse than publishing nothing, because somebody will believe it |

### ⚠️ Contract-tested, NOT live-verified — and the part that word hides

46 tests run the adapter and its diagnostic against the documented REST shapes. It has **not** been
run against a live Azure DevOps instance, and [docs/CONTRACTS.md](docs/CONTRACTS.md) records exactly
what that does and does not leave unproven, layer by layer.

The short version is more interesting than "we could not test it". A live run would prove **one**
path: the happy one, on one plan, with one person's permissions. Every failure that actually costs
somebody an afternoon is on the other paths — and those cannot be provoked on a live instance *even
with full access to one*:

| The failure | What provoking it live would require |
| --- | --- |
| a PAT with Code scope but not Test Management | issuing a deliberately broken token |
| a plan id that exists but is invisible to you | borrowing someone else's permissions |
| ⛔ a suite fence left behind by a plan reorganisation | reorganising a real plan |
| an anonymous call answered **203 + HTML**, not 401 | revoking a token mid-request |
| DNS / proxy / TLS interception | breaking your own network |

A stub produces all five on demand, and each one has a test. What genuinely remains unverified is
narrow and named: **the write path against a real plan.** That stays written down rather than quietly
implied — and the writes are behind `--arm`, which nothing defaults to.

⚠️ One of those tests exists because the others were not enough: every stub above resembles whatever
I assumed `fetch` does. Five more run the ladder through the **real global `fetch`** against a
loopback HTTP server, with no stub at all — because 24 tests passing against a fiction is precisely
the shape of failure this project exists to name.

### `--diagnose` — walk the chain one hop at a time

```bash
AZURE_TOKEN=<pat> nightbark sink:ado --org <o> --project <p> --plan <id> --suites a,b --diagnose
```

Read-only, so there is nothing to undo if it is wrong. Seven rungs — credential, organisation,
project, plan, suites, **the fence**, points — each reporting what it proved, and on a failure what
fixes it. Everything below a failure reports as `skipped`, because *unanswered* and *passing* are not
the same thing.

It exists because **the same status code means different things at different depths**, and one error
message cannot say both: a 404 on the organisation is a typo, while a 404 on the plan is usually
*permissions wearing a 404* — ADO answers 404 for a plan you cannot see. The 403 is the sharpest
example: it arrives only at rung 4, on a token that resolved the org and the project and would clone
repositories all day. "403 Forbidden" alone sends you hunting the wrong thing.

⛔ **Rung 6 is the one worth the whole command, because it is the only failure here that is silent in
normal use.** A plan gets reorganised into drops; a publish still scoped to the old suite ids matches
no points, writes nothing, and reports every case as a tick. Nothing in the output is *wrong* — there
is simply nothing where the writes should have been, and it can sit undetected for weeks. So rung 6
does not merely check that the ids resolve; when one does not, it lists the suites that **do** exist,
because the next question is always *"then what should it be?"*:

```
✖ 6. ⛔ the scoped suite ids still exist in the plan
     2 of 2 scoped suite id(s) are NOT in plan 764570: 865414, 865843.
     ⤷ fix: ⛔ This is the failure that reports success. A publish scoped to a suite that no
       longer exists matches no points, writes nothing, and ticks every case — the run
       output is not wrong, there is simply nothing where the writes should be.
       The suites that DO exist: 900001 (Drop1) · 900002 (Drop2)
       Resolve the ids at RUN TIME rather than pinning them.
```

⚠️ Rung 1 reports the credential's **length and character class only, never any part of its value** —
including when it is malformed. It recognises the five paste errors (shell quotes kept, the whole
`Basic …` header pasted, the variable *name* pasted, a copied newline, a leading colon) from shape
alone. A diagnostic that echoes a credential into terminal scrollback has turned a support question
into a rotation.

⚠️ And one behaviour worth knowing before any of this: an **empty** token is refused up front rather
than sent. Azure answers an unauthenticated call with **203 and an HTML sign-in page**, not a 401 —
parsed naively that becomes an empty result set, and the caller reports a clean run against a plan it
never reached.

## `triage` — fingerprint CI failures, then brief the judgement

```bash
nightbark triage playwright-report.json --out brief.md
```

Adopted from the `ai-bug-triage` discipline, split along the seam
[ADR-0007](docs/adr/0007-triage-is-a-gate-with-a-brief.md) draws: **steps 1-4 are a gate, steps 5-6
are a brief, step 7 is a person.**

| | | |
| --- | --- | --- |
| 1-4 | normalise · anchor · hash · cluster | pure functions, no model, no network |
| 5-6 | severity · category · root cause · ticket prose | a markdown brief any agent can answer |
| 7 | create / merge / close | **a human, always** |

⛔ **Deduplication is never a model's job.** Asked twice whether two errors match, a model may answer
differently — and a dedup that is not reproducible merges distinct bugs at random, hiding a live bug
behind a ticket somebody already closed. A SHA-256 of a canonical form answers identically every
time, which is the only property that makes a merge safe to *suggest*.

So nothing is filed. The output is groups and **links**, each carrying its score and the dimensions
that produced it:

```
  d0dcbd50b73c3907  x2   Error  ⚠️ flaky 2/2
      timeout 30000ms exceeded waiting for selector
      waitForSelector(login.ts)
  585186c83c38a0be  x1   TypeError
      Cannot read property 'vendorId' of undefined
      processOrder(order.ts) -> groupByVendor(order.ts)

  near-duplicates — SUGGESTIONS, not merges:
      585186c83c38a0be ~ e124dcf8dcc76c82  score 0.9 (duplicate)
          matched: exceptionType, messageTemplate, frames, component
```

Two failures in different test files, with different line numbers, recognised as one root cause —
and kept as separate fingerprints so you can still see which tests are affected.

### ⚠️ Writing it down found two defects the prose had held

- **The spec contradicts itself.** Step 2b says *"replace quoted strings with `<STR>`"*; Test 5
  requires `'name'` and `'email'` to stay distinct. Both cannot hold. Resolved by length — a short
  quoted token is part of the template, a long one is a specific. *Where a spec's example disagrees
  with its rule, the example is what somebody actually wanted.*
- **The reference Playwright extractor reads one level of suites,** and Playwright nests them — so
  every failure inside a `describe` block was silently skipped.

Neither is a criticism of the discipline; prose cannot execute. It is what
[ADR-0002](docs/adr/0002-gates-not-prose.md) means. The five fingerprint stability assertions are
tests now, and the clustering weights are asserted to sum to exactly **1.00**, because every
threshold is calibrated against that total.

## Installing

```bash
npm i -D nightbark        # once published
npm i -D /path/to/clone   # or straight from a checkout
npx nightbark             # either way
```

Verified by **building a tarball and installing it into a clean directory**, not by reading
`package.json`: all five subcommands run from inside `node_modules`, including `selftest`.

⚠️ `fixtures/` ships deliberately. `nightbark selftest` reads them, so without them an installed
package cannot prove its own gates fire — and that proof is the central claim. The first draft
excluded them to save 20kB, which would have shipped a CLI whose most important subcommand crashed
on a missing path. A consumer being able to run `npx nightbark selftest` and watch each gate fire on
a known-broken fixture is worth far more than the bytes.

`prepublishOnly` runs the full selftest, so a broken build cannot be published.

## `init` — what it scaffolds, and what it refuses

`npm init playwright@latest` already gives you a project, maintained by the people who write
Playwright. Competing with that would be daft. What is missing is the **structural decisions that
are expensive to retrofit** — the ones a suite gets wrong in week one and pays for in month six.

So the scaffold is small and every file is load-bearing:

| | Why |
| --- | --- |
| `tests/fixtures/pool.ts` | Per-worker identities by `workerIndex` — deterministic, no locks, no waiting. Retrofitting an allocator means touching every spec that hard-codes an address |
| `release()` | A stub that **announces itself**. An allocator without teardown moves the problem to the second run of the day, where the failure looks like a product bug |
| `tests/fixtures/index.ts` | The **only** route to an identity. If a spec can write a literal, one eventually will |
| `workers: POOL.length` | A hard ceiling. The pool **throws** rather than modulo-wrapping, because wrapping hands two workers one identity and the run passes while proving nothing |
| `tests/vacuous.spec.ts` | **Deliberately broken.** It passes and proves nothing; the audit flags it. A scaffold that ships entirely green teaches nothing about what the tool is for |

Three refusals, per [ADR-0006](docs/adr/0006-what-init-scaffolds.md): **no configuration surface**
(flags are where a generator's complexity hides), **no speculative furniture** (it teaches people to
delete generated code unread, and one day that is the allocator), and **no Playwright tutorial**.

Verified on the output, not assumed: `tsc --noEmit` clean, 2 specs collect, both CI files parse,
and the audit flags **only** the vacuous spec.

## CI — one definition, two platforms

[`ci/pipeline.mjs`](ci/pipeline.mjs) is the single source; `npm run ci:gen` emits
`.github/workflows/nightbark.yml` and `azure-pipelines.yml`. **A generator, not a lowest common
denominator** — each platform gets its own idioms (SARIF upload to Code Scanning on one side, task
groups on the other) from shared *intent*.

⚠️ **`npm run ci:check` is the load-bearing half**, and it runs in the selftest. A generated file
that is committed will be hand-edited eventually, and from that moment the "single source of truth"
is a lie nobody can see. The check regenerates, diffs, and fails the build — proven both ways: a
planted hand edit exits 1, and a regeneration clears it.

nightbark's own CI runs its own rules, in this order:

1. `selftest` — **first, deliberately.** A gate that cannot fail reports compliance it never
   verified, so gates are proven before anything is audited with them.
2. `selfcheck` — ADR-0001, no client-identifying content
3. `ci:check` — the generated files still match their definition
4. the unit tests
5. an audit of `fixtures/` — which contain deliberate defects, so a run finding **nothing** there
   means the tool is broken rather than the repo being clean

### ⚠️ What widening the targets actually bought

TIER-1 recorded that the three original targets were **too clean**: a deliberate demo, a careful
personal suite, and a reference app — unusually *good* code, with zero traceability ids, zero
floating assertions, zero swallowed exceptions between them. It said no further field-unvalidatable
gate should ship until the target set was widened. So it was: four **shipped products** whose suites
run under real delivery pressure.

Four hours of that found **six defects in nightbark**, three of them in the two places a tool is
least likely to look at itself:

| | What was wrong | How it was found |
| --- | --- | --- |
| 1 | ⛔ **`traceability` read 0 of cal.com's 53 specs and reported it clean.** cal.com names them `*.e2e.ts`; the gate's own `appliesTo` accepted only `.spec.`/`.test.` | counting the files it claimed to have read |
| 2 | **Four gates each had their own regex for "a test file"**, giving three different answers — the root cause of (1). Now one exported definition in [`src/testfiles.mjs`](src/testfiles.mjs) | fixing (1) properly instead of locally |
| 3 | ⛔ **`--fail-on=never` was silently ignored.** The CLI read only `--name value`, so `--name=value` fell through to the default — flipping CI exit codes with nothing said. An unknown flag now exits 2 | believing four scoped audits were scoped, and they were not |
| 4 | **`serialised-suite` scored 5% (5 of 98).** It conflated `describe.serial` with `workers: 1`, but files still run in parallel — Rocket.Chat uses it as house style in 73 files | a repo large enough for a house style to exist |
| 5 | **A sleep guard was missing from its third branch** — again. The poll guard went on `setTimeout`, later on `waitForTimeout`, and never onto named sleeps | a mail client polling with `await this.delay(500)` |
| 6 | **Then the fix for (5) introduced a false NEGATIVE**, which is the worse trade because nothing announces it. An over-eager poll guard hid a genuine sleep inside `for (const screen of SCREENS)` | the per-target counts dropping where no false positive had been reported |

Three false-positive classes came out of it, each now a near-miss fixture so it cannot regress:

- ⛔ **a sleep inside a `page.route()` handler is the stimulus, not the wait.** The test asserts a
  menu stays open *while* a load is slow — the delay is the condition under test, so "replace this
  with a wait on what you depend on" asks the author to delete their own test.
- **the deadline arm of a `Promise.race`** — a `setTimeout` whose continuation *throws* is a timeout,
  not a sleep. No loop, so the poll guard never covered it.
- **a named sleep as a poll interval**, the third branch of (5) above.

And one lesson that generalises past this tool: **an iteration loop is not a poll loop.** A sleep
inside `for (const x of xs)` is paid once per element and is as fixed as any other; only a loop that
*re-tests* something makes a sleep an interval.

### `shared-test-identity` scored 0% — and that is now the design brief

Three findings on the new targets, all false:

| | The literal | Why it is not a defect |
| --- | --- | --- |
| cal.com ×2 | `first+seats@cal.com` | attendee *payload* passed to a fixture that creates and tears down its own booking per test |
| Rocket.Chat | `mail@mail.com` | an export destination typed into a field, and a deliberately non-existent address in a forgot-password flow |

In **all three** the literal is an **inline call argument**. Its one historical true positive was
**bound to a named constant beside a pool it was not part of**. That is a far sharper signal than
*shared*, it needs resolution rather than matching, and per
[ADR-0005](docs/adr/0005-how-an-irregular-runs.md) a shape too ambiguous to be a gate is exactly
right as a candidate finder for an Irregular.

### ⚠️ `traceability` has no field data, and now that is MEASURED rather than assumed

Zero traceability ids across **seven** public repositories — 694 spec files actually read, after
fix (1) above. The synthetic target is not a convenience; there is genuinely nothing to measure
against in public code.

### ⚠️ One target is SYNTHETIC, and is kept in its own row

| Target | Findings | Expected | Match |
| --- | --- | --- | --- |
| `fixtures/targets/traced-suite` **(synthetic)** | 5 (2 error, 3 note) | 5 (2 error, 3 note) | **exact** |

No public Playwright repo carries requirement ids — measured as **zero** across all three real
targets — so `traceability` has no field data of its own. A purpose-built target with an explicit
[answer key](fixtures/targets/traced-suite/ANSWERS.md) fills that gap, and **its number is never
added to the real-repo figures**: a synthetic result measures the gate against my own expectations,
where only a real repo measures it against the world.

Its value is the five **correct** patterns it also contains, three of which broke earlier versions of
the gate: an inherited `Feature:`-line tag read as a clash, a defect reference on a parked test read
as a lying id, and a collection-neutral decision marker read as an exclusion.

### The Irregular, measured separately

| | Findings | True | Precision |
| --- | --- | --- | --- |
| Judge alone | 3 | 1 | **33%** |
| Judge + Moriarty | 1 | 1 | **100%** |

Moriarty **dropped one** claim and **downgraded another**. Without the adversarial pass this
Irregular would have shipped two wrong findings on its first run — and a reader sent to rewrite two
correct tests does not open the report a third time.

The one confirmed finding is a class **no gate could reach**:

```ts
if (page.url() === "/") {            // page.url() is ABSOLUTE — never "/"
  expect(hasScriptTag).toBeFalsy();  // unreachable
}
```

No `else` branch, so a test named *"should handle special characters in registration"* asserts
nothing on any path. Moriarty refuted its own best escape hatch from inside the same file — a sibling
test writes `new URL("/", page.url())`, which is only meaningful if the URL is absolute — then
**upgraded the headline** from "absent premise" to "unreachable guard, test asserts nothing" — via the
adversarial pass's optional `headline` field, because
that is independently verifiable and the fix is one line.

Locator resolution closed the gap Moriarty named by name: **8/8** locators resolved on the demo
target, **8/9** on the production BDD suite (up from 0/9), tracing through nested components,
inheritance, interface aggregates, getters, locator-returning methods and one-hop locals.

### What it cost: thirteen rounds of red/green, every failure mine

| Found by | Count | Examples |
| --- | --- | --- |
| A `silent` fixture, before any real code | 3 | a matcher matched inside a **string literal**; a `setTimeout` **definition** read as a call; `appliesTo` rejecting its own fixture |
| First contact with a real repo | 6 | a **React component** whose sleep was deliberate; a textbook **bounded poll** — the pattern the gate's own advice recommends; a **not-found probe** read as a shared account |
| The production suite | 4 | **wiki page ids** read as phone numbers (9 false positives of 20); boundary and wrong-locale **probes**; a number inside a **diagnostic string**; `waitForTimeout` as a **poll interval** — *the same bug already fixed on the other branch and not swept for* |

⚠️ **The ADR-0001 self-check caught me a second time, automatically.** Building the traceability
fixtures I populated them with **real client case ids**, copied straight out of the live suite without
thinking. The `selfcheck` added two days earlier fired on all 23 of them before they could ship.

It also surfaced a real design question rather than just a leak: a *synthetic* case id is
indistinguishable **by shape** from a real one, so the shape rules flagged every legitimate fixture
too. Resolved by suspending the **shape** rules under `fixtures/` while keeping the **denylist**
active there — a shape rule guesses, a named term is certain — and proven both ways.

⚠️ **And one earlier leak of my own.** Documenting the page-id defect, I pasted a real client page id into
this README — and then into a gate comment. The `selfcheck` I wrote to enforce
[ADR-0001](docs/adr/0001-no-client-code.md) **missed it**, because it matched `@ado_123456` notation
and not a bare digit run in a URL path. Fixed the leak, added the shape rule, and the new rule
immediately found the second copy I had not noticed. Never committed.

### ⚠️ `shared-test-identity` is demoted, on evidence

12% precision on first contact; 33% after seven rounds of noise rules. Below the bar this project set
itself, so it reports as a `note` that asks a question rather than an `error` that declares a defect.
Three populations are indistinguishable on the line — a **managed** pool handed out per worker behind
a lock (correct), a **probe** value reused deliberately (coverage), and a **raw** hard-coded account
(the defect) — and only the surrounding mechanism separates them.

Its one genuine finding is the design brief for turning it into an Irregular: a spare value **defined
as a constant beside a pool it was not part of**. An allocator existed and this value sat outside it;
the suite's own notes record it causing a real concurrent-run failure. *Shared **and** outside the
allocator that exists* is a far sharper signal than *shared*.
